# 10.1 · git y el agente — solución de referencia

## La costumbre que sostiene todo el curso

**Trabaja sobre git limpio y en una rama.**

```bash
git status                      # sin cambios pendientes
git checkout -b prueba-agente
```

No es ceremonia de proceso. Una rama convierte cualquier resultado —bueno, malo o
incomprensible— en algo que se descarta con un comando. Sin ella, quince archivos
modificados que no acaban de funcionar son una tarde de deshacer a mano.

Con esa red puesta puedes darle permisos más amplios y dejarle iterar más, que es
cuando estas herramientas rinden. La gente que las usa con miedo suele ser la que
no tiene dónde caerse.

## Qué delegar entero

| Tarea | Por qué compensa |
|---|---|
| Leer el diff y contarte qué cambió | Llegas a tu revisión sabiendo dónde mirar |
| Preparar el borrador del mensaje de commit | Lo redacta bien; tú lo apruebas |
| «¿En qué commit se introdujo esto?» | Ejecuta `git log` y `git bisect` e interpreta |
| Encontrar cuándo cambió un comportamiento | A mano son veinte minutos; con él, dos |

Investigar el historial es donde la diferencia es mayor. Escribir código es donde
más se le mira; investigar es donde más ahorra.

## Qué no delegar nunca

**Publicar el mensaje de commit sin leerlo.** Es el registro que va a leer alguien
dentro de un año, tú incluido.

**Resolver conflictos de fusión.** Un conflicto es dos intenciones que chocan, y
la información para decidir cuál gana casi nunca está en el código.

**Cualquier cosa contra la rama principal.** `push`, `rebase`, `reset --hard`.
Por eso están en la lista de denegados de la plantilla.

## El checkpoint 10.2

Deja que prepare un commit y **léelo antes de aceptarlo**. Lo que vas a ver casi
siempre: un mensaje correcto en la forma y genérico en el fondo — describe el
diff en vez de decir el motivo.

Corregir eso es lo que después se convierte en una regla del `CLAUDE.md`, y así
se cierra el círculo que empezó en el módulo 1.
