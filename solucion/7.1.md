# 7.1 · Un servidor MCP — solución de referencia

## Por dónde empezar

**Por el que te ahorre el copiar y pegar que más repites.** Si cada día pegas
resultados de consultas, empieza por la base de datos. Si pegas descripciones de
incidencias, por el gestor de incidencias.

Empezar por «el que parece más potente» lleva casi siempre a tener conectado algo
que no usas, con el coste de contexto que arrastra.

## La configuración, con la credencial fuera

`.mcp.json` en el proyecto (versionado):

```json
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": { "DATABASE_URL": "${DATABASE_URL_READONLY}" }
    }
  }
}
```

**La clave nunca dentro.** El archivo referencia una variable de entorno que cada
persona tiene en su máquina. Un `.mcp.json` con una credencial escrita es una
credencial publicada en cuanto alguien clone.

Fíjate en `READONLY`: en la mayoría de los casos basta con solo lectura, y esa
decisión de treinta segundos limita el alcance de cualquier error posterior.

## Lo que gana de verdad

No es ahorrarte el copiar y pegar: es que puede **iterar**. Ve el resultado, se
da cuenta de que la consulta no era la correcta, prueba otra. Eso con copiar y
pegar cuesta tres rondas tuyas.

## El coste que no se ve

Cada servidor conectado **mete sus herramientas en el contexto de cada sesión**,
la uses o no. Con cinco servidores medianos, una parte notable del presupuesto se
va describiendo capacidades que no vas a usar hoy — y ese espacio sale del que
tenías para tu código.

Revisa cada pocos meses qué tienes conectado y quita lo que no invoques.

## La confusión frecuente

Montar un servidor MCP para algo que ya se puede hacer con un comando. Si `psql`
está instalado y el agente puede ejecutarlo, quizá no necesitas el servidor:
necesitas el permiso.

MCP es para lo que **no** es tu máquina — un sistema externo con su propia
autenticación.
