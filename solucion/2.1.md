# 2.1 · Permisos — solución de referencia

## La configuración que se copia del curso

`plantilla/.claude/settings.json`. La parte que conviene entender es la de
denegados:

```json
"deny": [
  "Read(.env)",
  "Read(.env.*)",
  "Read(**/*.pem)",
  "Read(**/credentials*)",
  "Bash(git push:*)",
  "Bash(rm -rf:*)"
]
```

Seis entradas, dos categorías: **lo que no debe leer** (credenciales) y **lo que
no tiene vuelta atrás** (publicar, borrar recursivamente).

No es por desconfiar del agente. Es que un comando razonable con una ruta mal
deducida hace algo irreversible, y esas seis son donde «irreversible» duele.

## Por qué los patrones son específicos

```json
"Bash(git diff:*)"     ← permite cualquier git diff
"Bash(git:*)"          ← permite también git push, git reset --hard...
```

Una lista de permitidos cómoda **y** segura se consigue con granularidad. Un
permiso amplio para «cualquier npm» incluye `npm run <script>`, y ese script
puede hacer lo que sea.

## Los dos extremos, y por qué cuestan igual

**Aprobar todo a mano** → a la media hora aceptas sin leer. Tienes la fricción
sin la seguridad, que es lo peor de los dos mundos.

**Permitir todo** → funciona hasta el día que no.

El punto medio: lo que lee, permitido. Lo que escribe dentro del proyecto,
permitido. Lo irreversible, denegado siempre.

## El checkpoint 2.3, y por qué es manual

Ver una petición de permiso y **denegarla** enseña algo que no se puede leer:
qué pasa después. El agente no se rompe — busca otro camino, o te dice que sin
eso no puede seguir. Saber eso quita el miedo a decir que no.

## Dónde va cada cosa

- `.claude/settings.json` (versionado) — las **denegaciones**. Aplican a todos.
- `.claude/settings.local.json` (sin versionar) — tus permisos de comodidad.
- `~/.claude/settings.json` — lo tuyo en todos tus proyectos.
