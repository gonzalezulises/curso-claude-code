# 4.1 · Una skill para tu proyecto — solución de referencia

## La del curso

`plantilla/.claude/skills/revisar-pr/SKILL.md`. La parte crítica es la cabecera:

```yaml
description: >-
  Revisa un pull request de este proyecto siguiendo su checklist. Úsalo cuando
  se pida revisar un PR, revisar cambios antes de mergear, o comprobar si una
  rama está lista.
```

**Esa frase es lo único que el agente lee para decidir si le sirve.** Fíjate en
que enumera las formas en que la gente pide realmente esa tarea, no lo que la
skill hace por dentro.

Compara: «Ayuda con revisiones de código» no le sirve para decidir nada.

## Regla, comando o skill

Las tres son texto que influye en el agente. Se distinguen por **cuándo entran**:

| | Quién la activa | Ejemplo |
|---|---|---|
| **Regla** (`CLAUDE.md`) | Nadie: vale siempre | «El SQL va parametrizado» |
| **Comando** (`/nombre`) | Tú, explícitamente | «Revísame el diff» |
| **Skill** | El agente, si encaja | «Cómo se prepara una versión» |

## La pregunta que decide

**¿Lo explicarías igual a alguien nuevo cada vez?**

Si sí, es un procedimiento → skill. Si cambia según el caso, es criterio →
reglas.

Procedimientos: preparar una versión, revisar un PR, añadir un idioma.
Criterios: qué estilo usamos, qué no se toca, cuándo algo está terminado.

## Cómo saber si se está usando

Pide algo que debería activarla y mira si la menciona. Si no aparece, el problema
está en la descripción, **no en los pasos**. Es la misma comprobación que la del
módulo 1 con las reglas, y por la misma razón: una skill que nunca se invoca está
escrita pero no vive.

## Tamaño

Una pantalla de pasos, más los archivos de apoyo que hagan falta. Si el
`SKILL.md` se va a cinco pantallas, probablemente son tres procedimientos.
